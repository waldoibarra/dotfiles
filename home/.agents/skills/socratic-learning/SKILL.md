# Socratic Learning

- **IS:** a portable teaching method for orientation, learning, and learning-oriented maintenance.
- **IS NOT:** learner tracking, curriculum storage, global coaching records, or automatic
  repository edits.

Use the lightest mode that matches the request.
Do not force a quiz for an ordinary quick factual lookup.
Preserve the learner's option to stop, orient, or switch mode.

## Modes

- **Orientation:** map the territory, sequence, prerequisites, and useful connections.
  Do not teach every term or claim mastery from orientation.
- **Learning:** teach one concept or objective.
  Verify fresh prerequisites, reasoning, concise synthesis, and independent application.
- **Maintenance:** update domain docs or procedure after scoped approval where required.
  Do not continue a lesson or create learner records.

## Teaching Loop

1. Confirm the mode, topic, and smallest useful objective.
2. Check prerequisite concepts afresh before relying on them.
3. Ask for open reasoning before hints or answers.
4. Ask one question or propose one action, then wait.
5. If the learner is stuck, give a graduated hint, counterexample, or checked fact.
6. Correct false premises with verified evidence; state what remains unknown.
7. Explain foundations directly when questions are insufficient.
8. Avoid endless guessing; switch to explanation after useful attempts.
9. Ask for an accurate own-words synthesis, normally at most 17 words.
10. Check distinct application in a new example, contrast, or situation.
11. Advance only when synthesis and application support current-session understanding.

The 17-word synthesis is a default learning checkpoint.
Local project instructions may set a different explicit constraint.
The teacher's explanations and application checks need not fit 17 words.
Count whitespace-separated words; attached punctuation adds no word.
Do not rewrite the learner's answer and treat your rewrite as evidence of their understanding.

## Knowledge and Scope

Use checked facts from code, docs, sources, or observed results.
Never fabricate mastery, retention, progress, scores, or tracking state.
Previous sessions and confident answers never prove present understanding.

Curiosity-led domain docs may grow when the learner asks deeper questions.
Before editing, verify the repo permits that scope and approval level.
Resolve the owning topic folder from the repository index and instructions.
The teacher manages file organization.
Ask the learner only when the learning goal or authorization is genuinely unclear.
Do not repeatedly ask permission for factual expansion already approved by local rules.
Behavior changes, harness changes, publication, and cross-repository edits require scoped approval.

## Approval and Routing

- Use `session-improvement` for reusable workflow changes after approval boundaries are clear.
- Use repository instructions for local persistence, tests, commits, and push rules.
- If a required teaching skill, source, or repository rule is unavailable, report the blocker.
- Keep private identity, project, and learner details out of global reusable material.

## Gotchas

- A short answer can be memorized; require independent application.
- A long answer can be thoughtful; teach precision without treating length as failure.
- Repeating corrected wording is practice, not proof of durable understanding.
- Orientation is not a lesson completion state.
- Maintenance edits are not authorization to teach, track, commit, or publish.

Maintenance only: `evals/evals.json` holds routing and regression scenarios for skill changes.
Format checks do not prove behavioral teaching quality.
