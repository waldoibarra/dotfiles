# Improvement placement

Read before drafting an improvement proposal.
Choose the existing owner before creating a file, skill, or process.

## Classify three axes

**Scope:** personal or work.

- Personal dotfiles travel across workplaces and affect their co-users.
- Workplace harnesses belong to that workplace's team.
- Remove workplace names, tools, repositories, and people before considering a rule personal.
- If the rule loses its meaning, keep it work-scoped.
- Keep work evidence and work-only mechanics out of personal configuration.
- Personal preferences enter workplace configuration only with that team's approval.

**Harness:** neutral or specific.

- Prefer shared instructions and portable skills for reusable behavior.
- Use native configuration only for harness-specific mechanisms, including hooks, settings, and
  model controls.
- Credentials and runtime state stay harness-native.

**Audience:** private, dotfiles co-users, or workplace team.

- Name who will load the change.
- Keep individual preferences private unless sharing is approved.
- Write shared rules generically, without naming individuals.
- State unsettled axes as assumptions; never silently guess.

## Respect the local loop

Read repository instructions and their linked workflow or maintenance documents before proposing
changes.

Identify:

- The closure trigger and permitted home for proposals.
- Recording rules and pre-approved change classes.
- Verification, commit, and publication policy.

- Inside the repository, its local loop controls records and delivery.
- Use its route for pre-approved changes; reserve other changes for scoped approval.
- Where local rules are silent, shared harness rules apply.

- Outside the repository, the local loop is evidence, not global policy.
- Require cross-repository evidence and explicit approval before promoting its rules into shared
  instructions, skills, or dotfiles.
- Name the second repository showing the friction; otherwise target the local owner or propose
  nothing.
- A repository's adaptation of a global skill remains locally owned.

## Store only permitted records

- Project knowledge belongs in the project's documentation, plans, or skills.
- Harness mechanics belong in the owning workspace's documentation or plan.
- Shared reusable rules belong in global instructions or portable skills.
- Retain unanswered proposals only in an existing permitted plan, never a new global log.
- Without a permitted plan, leave the proposal in the reply only; persist nothing.
- Keep identity, family details, work secrets, and project-private facts out of reusable guidance.
- Respect the repository's domain layout; do not impose another project's structure.
- Edit canonical sources and link consumers; reuse existing mechanisms.
- Add no hooks, daemons, schemas, dependencies, or updater paths merely for observation.
