# OpenSpec in the shared harness

**Agree before building; keep the agreement available to the next agent.**
OpenSpec owns scoped change artifacts, not personal roadmaps or general research archives.

Read [the session workflow](session-workflow.md) before classifying a request or starting a change.
Prototypes remain outside OpenSpec; only the durable-change route uses its artifacts.
Shared approval, communication, and documentation rules apply to authored `openspec/` artifacts.

## Work through ordinary conversation

Ask the agent to refine the task, compare alternatives, and propose a plan.
The shared planning gate routes refinement through `grill-with-docs`.
OpenSpec skills use the native CLI; specialist skills improve reasoning without creating another
authoritative plan.
Explicit approval starts implementation; feedback requests revision.

No slash commands are required.
Skills-only delivery removes generated command files, not the CLI dependency.
Agents must report missing skills or tools rather than silently approximating their behavior.

For an existing OpenSpec project, agents read its configuration and current change before
continuing.
Initialization of another repository requires explicit authorization; global skill discovery does
not initialize projects.

## Keep ownership explicit

| Location | Owner and purpose |
| --- | --- |
| `home/.agents/` | Shared harness instructions, authored skills, roles, references, and MCP configuration |
| `.agents/skills/openspec-*/` | Unmodified skills generated by the OpenSpec CLI |
| `openspec/config.yaml` | Project-specific context and native schema selection |
| `openspec/schemas/session-workflow/` | Shared custom artifact contract, linked to the session guide |
| `openspec/changes/<name>/` | Proposals, tasks, and conditional behavior specifications |
| `openspec/specs/` | Maintained behavior specifications |
| `openspec/changes/archive/` | Completed native changes |
| Concern-specific documentation | Current operational explanations and procedures |
| Life vault | Personal priorities and cross-repository coordination |

Separate design files belong only to schemas requiring them or warranted supporting detail.

`openspec/` is the upstream default.
Do not invent roadmap or legacy subdirectories inside it.
Existing records remain source evidence; convert only the scope of an actual change.
The full historical-document migration is deferred to the next documentation session.

## Provision both machines

Mise owns `npm:@fission-ai/openspec` at `latest`.
Dotbot links `home/.config/openspec/config.json` into the user's native OpenSpec configuration
directory.
Pi and Cursor discover the generated skills through `~/.agents/skills/`.
Claude Code receives links to the same source through `~/.claude/skills/`.
No separate Cursor skill copy or custom adapter is required.

Dotbot also links the schema into `~/.local/share/openspec/schemas/session-workflow`.
The session guide is linked as `~/.agents/references/session-workflow.md` for portable schema
instructions.
Dotfiles selects this schema for new changes; existing changes retain their recorded schema names.
Other repositories require explicit adoption; a project-local schema takes precedence over the
user-level copy.

The updater runs the native preview before refreshing this checkout's generated skills.
Matching output is a no-op; upstream version changes may modify tracked generated files.
Review those changes before committing.
The updater does not initialize or update unrelated repositories.

Run `dots` under the existing [workstation-sync boundaries](/docs/tooling.md#sync-the-workstation).
Each machine must reload its clients afterward and verify effective skill discovery.
One machine's checks do not establish the other machine's installation or behavior.

Anonymous telemetry is disabled so native commands do not add machine identifiers to tracked
configuration.
Native config commands can modify the linked tracked file.
Keep portable preferences there; credentials, stores, session state, and machine-specific paths stay
local.

## Verify the change

Use native commands for artifact state and structural validation:

```sh
openspec status --change adopt-openspec-harness
openspec validate adopt-openspec-harness --strict --no-interactive
python3 scripts/tests/test-agent-harness.py
python3 scripts/tests/test-openspec-sync.py
python3 scripts/tests/test-openspec-schema.py
openspec schema validate session-workflow
```

Structural validation does not prove approval compliance, implementation correctness, or successful
multi-agent collaboration.
Test a fresh-session handoff separately before claiming those outcomes.

## Maintain the schema with the workflow

Read [workflow evolution](session-workflow.md#evolve-the-workflow-from-evidence) before changing
artifact responsibilities.
The schema references the installed guide; the guide links back to the maintained schema source.
Neither link authorizes changes or replaces the native compatibility checks.
Revert `openspec/config.yaml` to `spec-driven` to stop selecting the custom schema for new changes.
Keep the shared schema available while any existing change still references it.

## Collaborate without conflicting writes

The [shared orchestration
reference](/home/.agents/references/orchestration.md#coordinate-across-harnesses)
owns lead and worker responsibilities.
Read [Herdr coordination](/docs/agent-integrations.md#cross-harness-coordination) before
terminal-controlled handoffs.

One lead reconciles worker results and owns canonical task updates, spec synchronization, and
archiving.
Use separate worktrees for parallel writers and exchange revisions explicitly.
A terminal message is transport, not a replacement for the approved change artifact.
